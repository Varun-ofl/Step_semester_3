Session 8 Concept Answers

Question 1
The email field should be private, and external code should not be able to assign it directly. The User class should expose a changeEmail method that validates the format and checks uniqueness before replacing the current value. This protects the object's invariant that every user has a valid, unique email address. Unrestricted access could introduce null, malformed, or duplicate email values and leave the object in an invalid state. Controlled access keeps validation in one place and ensures every successful change preserves a valid User state.

Question 2
Inheritance is appropriate when every report truly is a specialized kind of one common report with shared state and behavior. Optional capabilities such as DataExport and DataVisualization are better modeled as separate interfaces because they are independent features that different report types may support in different combinations. A single inheritance hierarchy containing every capability would force reports to depend on behavior they do not need and would become difficult to extend. ReportingService can work with the core report abstraction while checking or receiving the optional capability interfaces when those features are required.

Question 3
NotificationService should depend on a Notification interface with a send method. EmailNotification, SMSNotification, PushNotification, and future notification types implement that interface. The service receives a Notification object and invokes send polymorphically, so it depends on the abstraction rather than concrete classes. Method overriding supplies each channel's behavior, and runtime polymorphism selects the correct implementation. Adding InAppNotification only requires implementing the interface and does not require changes to the existing service workflow.

Question 4
Organization and Department are best modeled with composition because departments are owned parts of the organization and are dissolved when the organization is dissolved. Department and Employee are better modeled with aggregation because employees can continue to exist and can be reassigned to another department when a department is removed. The difference is lifecycle ownership: composition means the part depends on the whole for its lifecycle, while aggregation represents a weaker whole-part relationship where the part has an independent lifetime.

Question 5
The UML multiplicity is Student 0..* to Course 0..*, because a student may enroll in many courses and a course may have many students. The relationship can be implemented through an Enrollment association class or a controlled enrollment collection. The rule that a student cannot enroll in the same course more than once is a business constraint, not a multiplicity statement. Multiplicity describes the allowed number of related objects; application logic, a uniqueness constraint, or a composite key such as (studentId, courseId) enforces the no-duplicate enrollment rule.
